## 一、项目背景：AI 结对编程的"多对话失明"问题

大语言模型编程助手普及后，开发者普遍开起了**多个并行 AI 对话**：A 对话改代码、B 对话跑调试、C 对话写文档。问题随之而来——

- **互相看不见**：三个对话各自为政，A 不知道 B 已经修了某个 bug，重复劳动；
- **任务撞车**：两个对话同时改同一个文件，互相覆盖；
- **独占资源抢夺**：编辑器、调试器、模拟器同时被多个对话操作，状态互相破坏；
- **口头派活无留痕**：开发者在一个对话里对 AI 说"顺便把 X 修一下"，其他对话对此一无所知；
- **掉线即失联**：一个对话窗口关掉，它做到一半的工作无人知晓、无人接管。

传统项目管理工具（Jira、Trello）为人类团队设计，操作成本高，AI 对话既不会主动去用，也无法无摩擦集成。**Agent Board 的核心思路：把看板做成项目根目录下的一个纯文件夹，让 AI 对话用一条 shell 命令就能读写，让并发安全由操作系统级的 POSIX 原子锁保证，让人随时能用一个命令看到全局。**

## 二、技术架构

### 2.1 零依赖的文件看板

看板数据落盘在项目根 `.agent-board/` 目录，纯文件、无服务、无数据库：

```
.agent-board/
├── tasks/T-0001.json …   # 任务卡（原子写入）
├── locks/*.lock          # 认领锁（O_CREAT|O_EXCL 抢锁）
├── events.jsonl          # 全员操作流水（事件溯源）
└── config.json           # 可选配置（锁超时秒数等）
```

### 2.2 POSIX 原子锁：并发安全的根基

- **认领即抢锁**：`claim` 通过 `open(O_CREAT|O_EXCL)` 创建锁文件，操作系统保证同一瞬间只有一个进程成功——两个 AI 同时抢一单，必然一胜一败，绝无灰色地带；
- **任务 ID 同理**：并发 `add` 也不会撞号；
- **租约语义**：锁文件 mtime 超过 `stale_seconds`（默认 1800 秒）视为原认领者离开，其他 agent 可 `steal` 接管；长任务用 `touch` 续约防误夺。

### 2.3 双通道接入：CLI + MCP server

- **CLI**：`board.py` 纯 Python 标准库（3.9+，零第三方依赖），任何能跑 shell 的 AI 对话直接调用；
- **MCP server**：内置 12 个 `board_*` 工具的原生 MCP 实现，支持 MCP 协议的客户端可结构化调用；
- **skill 自动触发**：ZCode skill 在"多对话协作/接任务/派任务/看板"等场景自动引导 agent 使用，无需记忆命令；
- **人类视图**：`/board` 自定义命令 + `board_overview.py` 固定口径总览脚本，人类一眼看清全局。

### 2.4 客户端无关

已在 ZCode 与 Codex 两类客户端实测兼容。接入三层递进：CLI 零门槛（任何 agent）→ skill 拷贝即装 → MCP 注册。不锁定任何厂商生态。

## 三、核心功能

| 命令 | 作用 | 并发安全机制 |
|------|------|--------------|
| `add` | 建任务（支持优先级/父任务/描述） | O_EXCL 防撞号 |
| `claim` | 接任务（自动挑最高优先级待办） | 原子锁防抢单 |
| `done` | 交付并写结果摘要 | 仅认领者本人可提交 |
| `comment` | 留言交接/进度续约 | 追加写 |
| `feed` | 全员最近操作流水 | 事件溯源 |
| `steal` | 接管超时任务 | 锁 mtime 判定 |
| `touch` | 长任务续约 | 刷新锁 mtime |
| `release` | 归还任务回待办池 | 释放锁 |

特色机制：

- **boss 频道**：`--agent boss` 的任务与留言视为项目所有者直接指示，全体 agent 必须优先响应；人类在任何对话里的口述由当值 agent 代为落板，保证"说过的每件事都在板上"。
- **人工总览双视图**：`board_overview.py` 以固定口径输出全项目进度（总进度/在飞 agent/逐单状态），消除不同 agent 查询切片不一致导致的信息偏差。
- **常驻租约**：独占资源（编辑器/调试器/模拟器）以常驻任务形式建模为租约——用前 `claim` 持有、用完 `release` 归还，从机制上杜绝资源争用。
- **实测队列**：需要操作共享环境（如运行游戏）的请求以队列任务串行执行，由当值操作员统一消化。

## 四、应用场景

1. **多对话并行开发**：多名"数字员工"（不同模型、不同分工）围绕同一仓库协作，看板是唯一的协作事实源；
2. **单对话多 worker**：大任务 `add --parent` 拆子任务，并行 worker 各自认领，主对话只看结果；
3. **人机混合团队**：人类以 boss 身份进板派活、验收、发通报；AI 以各自身份接单、回报；
4. **跨工具协作**：ZCode、Codex 等不同 AI CLI 的对话共用同一块板，客户端无关。

## 五、创新点（对应评审维度）

**技术创新（30%）**
- 用 POSIX `O_CREAT|O_EXCL` 文件锁实现 AI agent 间的任务互斥，不依赖任何外部服务或数据库；
- 事件溯源式流水（events.jsonl）+ 租约语义（touch/steal）完整建模了"AI 工作者会掉线"这一现实问题；
- 纯标准库实现（Python 3.9+），零依赖即零供应链风险。

**场景落地（30%）**
- 已在真实多对话开发项目中全程使用：5 个并行 AI 对话、2 天内流转 24+ 看板任务，原子锁期间任务零撞车；
- 覆盖从"接单-开发-交付-验收-发布"的完整工作流，含事故驱动的规则演进（见第六节）。

**开源治理（20%）**
- MIT License，公开仓库 + marketplace 一键安装 + CHANGELOG 版本化；
- 文档完备：主 README、插件内 README、SKILL.md、安装脚本齐备。

**长期发展（20%）**
- v0.3 规划：审核门禁（任务完成需审核通过才闭环）与成果回退流程化；

## 六、真实应用案例（脱敏）

本项目插件在开发一个中型模拟器游戏软件过程中全程"吃自己的狗粮"：

- **规模**：5 个并行 AI 对话（不同模型分工：写代码/跑调试/写文档/当操作员），持续多天，看板流转任务 24+，事件流水数百条；
- **防撞车实效**：多个对话多次同时试图认领/修改同一模块，原子锁与"先声明后动手"规则下零次任务撞车；
- **资源租约的诞生**：多个对话争用同一编辑器与运行实例，曾相互停掉对方的调试进程；事故后团队将"编辑器独占租约"固化为看板常驻任务，争用归零——**规则由真实事故驱动、固化进协作协议**的过程本身就是看板价值的证明；
- **人类在环**：项目所有者以 boss 身份在任意对话口述需求，由当值 agent 落板派发；验收以"操作员实测通过"为触发条件驱动发布流程，全程板上留痕。
